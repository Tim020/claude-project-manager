# Project Assistant

Design 9a, being built in steps; see [`design/Project Assistant Backend.md`](../design/Project%20Assistant%20Backend.md). The left rail's Assistant tool (⌘3) follows the selected session's project.

- **Notes:** press ⇧⌘N anywhere (File → New Note) to open the capture box, linked to the session you're in. For a thought that isn't about that session, such as a new feature, click the × beside "Linked to…" to save it unlinked. Save Note (⌘↩) saves it straight away; Esc cancels. Notes are listed newest first, each with its author (you, the assistant or a session), the session it came from or was linked to, and its age. A long note shows its first 5 lines, with **Show More** to open it (its text is selectable once it's open). What the assistant has done with a note, or failed to do, shows in a row under it: **Checking against the plan…**, a **Suggests a plan item** or **Suggests attaching** chip, a failed check, or the plan item it's attached to. Notes the assistant or a session wrote have Undo. A note's **⋯** menu (top right, or right-click the card) copies it, checks it against the plan, adds it to the plan, attaches it to a plan item or detaches it, or deletes it.
- **Plan:** the Plan | Notes switch shows the plan, grouped as In Session, Planned, Ideas and Done, each row with its notes count. The plan grows out of your notes: **Check Against Plan…** on a note (also in its ⋯ menu) checks it against the plan and suggests either a new item ("Create a plan item from this note?") or an existing one it duplicates ("Attach this note to an existing plan item?"). The note shows a chip for it, which opens the question in a popover with the assistant's reason ("Reads like a bug.") and the item it means on lines of their own. Nothing changes until you click Create Plan Item or Attach; Keep as Note dismisses it, and **Check Again** asks afresh. Suggestions stay on their notes across a relaunch, as long as they still apply. A promoted item takes the title the check suggested (or, without one, the note's first sentence). If you disagree with a suggested duplicate, **New Item Instead** makes a new item anyway, and **Add to Plan** (in a note's ⋯ menu) adds it without the check. Click an item for its status (change it from the pill), title (double-click to rename) and attached notes, or to delete it (its notes stay). Right-click a row to move it between statuses.
- **The check:** one short Claude call (Haiku by default, no tools, nothing saved as a session). In a project set to Automatic (the default), a note you capture is checked straight away while plan usage is under the threshold in **Settings › Assistant**; over it, the check waits and runs once usage drops. There you can also turn the assistant off everywhere (a note's link then reads **Add as Idea**, and adds it without asking Claude), set the threshold (80% of the 5-hour or weekly limit by default), and allow background work while using credits. Check Against Plan… that you press always runs. Each call is listed in the Activity Log.
- Notes and plan items aren't in folders. The only place a folder comes in is the session you start from an item.
- **Start Session from a plan item:** a Planned item or Idea has **Start Session**, which opens New Session from Plan: its name, a folder for the session (Unfiled until you pick one), tags, worktree toggle, and a preview of the opening prompt, which is the item's title, its notes (oldest first) and its GitHub issue, then "Use these skills: /…" in blue. The skills are chips, picked in code from the project's approved skills (a skill's `paths` matching files the item's sessions changed, or its `metadata.claudio-folders` naming the folder picked for the session or one of its parent folders; at most 3). Removing a chip only leaves that skill's name out of the prompt. The item then moves to In Session, and its view shows the session (click to open it) and the skills its prompt named. A session started before the assistant shows a hint instead, since it can't use skills or write notes. Chips also count the files the item's sessions edited (read from their history) and how many sessions in the chosen folder, or nested under it, used each skill.
- **Follow-ups:** in an Automatic project, when a session looks done, its card offers a follow-up: "<session> looks done. Follow up on what it did?" with **Follow Up** and **Not Now**. It looks done by Claude Code's own signals: its turn ended normally (not cut short by a usage limit or an error), it isn't waiting on you, and Claude Code says its task is done or ready for review, or you stopped it or closed its tab. A session whose context was compacted is offered one at its next pause too, even mid-task; unless Claude Code also says its task is done, that card says "<session> is using a lot of context. Follow up on what it's done so far?" instead. Something worth a look must also have happened since the last follow-up: changed files, a failed tool call, a commit, a `gh pr` command, a correction ("no, …", "next time…"), or 3 or more prompts. Offers cost nothing, and a new prompt in the session withdraws one. **Follow Up** asks Claude (one Claude call, Sonnet unless the project's Assistant Settings choose another, reading a digest of the session built from its history, never the whole transcript). The card then lists the notes it saved (untick one to remove it) and the plan changes it suggests (**Add n to Plan** applies the ticked ones). **Later** or ✕ sends it to **Needs You** in the Assistant panel, where unanswered offers, failed follow-ups (with Try Again) and plan changes sessions suggested also wait, counted by the rail's blue badge. **Review This Session** (in the session's ⋯ menu) asks straight away, in Manual mode too. Sessions from before this build start with nothing to follow up.
- **Skills:** a follow-up can also find a lesson, something future sessions should know that was learned the hard way (a failing command and what worked, or something you corrected). It must point at the failures and corrections in the session's digest, and Claudio groups lessons by what happened, not by the wording. Once the same lesson comes up in two sessions, or you told Claude to remember it, a skill is drafted (one Claude call, Sonnet by default): in the background in Automatic mode (behind the usage threshold), on **Draft Skill** in Needs You in Manual mode, and straight away for "remember this". The draft prefers changing an approved skill to adding one. Claudio checks it before you see it (a proper name that isn't Claude Code's own, lengths, and no secrets) and drops one that fails, logging only its name and the check. A draft that passes waits in Needs You as **New Skill** or **Changed Skill**, with why, the text as added lines or a diff, and **Approve**, **Edit** and **Not Now**. Files it names that aren't in the repository, and commands it runs that aren't installed, are listed on it under **Check Before Approving**. Nothing loads a draft until you approve it; then every Claudio session in the project picks it up within a few seconds. **Skills** in the panel's ⋯ menu lists the approved skills, how many sessions used each and when it changed, with each one's text and earlier versions. Lessons still waiting for a second session are listed there too, with **Draft Now** to draft one straight away. With Don't send transcripts on, follow-ups find no lessons. A note whose background check failed says so, and opens Job Failed with Try Again. Skills say which session tags they suit, so a session's tags help pick its chips. **Save to Repository** (on a skill's view) moves a skill into the repository's `.claude/skills`, yours to commit; the Skills list shows the repository's own skills too. A session started from a plan item with skills chosen loads only those (its own skill set, editable from the item's view); with none chosen it gets every approved skill. If a skill Claudio manages is changed or deleted outside it (by a session, or in the repository), Needs You shows what changed and who, with **Keep Change** or **Revert**. Once a day, a skill no session has used for 30 days is offered for retiring: **Retire** stops any session loading it, and **Restore** in Skills brings it back.
- **GitHub issues** (with `gh` installed and signed in, in a project on GitHub): a plan item without an issue has **Create GitHub Issue**, which runs `gh issue create` in the project's repository, titled as the item, with its notes as the body (oldest first; the title when it has none), and links the new issue to the item ("#50"). It's the only thing Claudio writes to GitHub. The item then shows its issue (Open, Closed, or Not found) and the pull requests that close it or that its session opened; each opens on GitHub. While the project's assistant is on (Automatic or Manual), linked issues are read every 10 minutes, and when an item is opened, in one `gh api graphql` call: state, why it closed, labels and closing pull requests. When a pull request that closes an item's issue is merged, its issue is closed, or a pull request its session opened is merged, Needs You suggests **Mark Done** with the evidence ("PR #14 was merged into main as 352ddc7, closing issue #19."). Mark Done moves the item to Done; **Not Yet** isn't asked again for the same evidence, only for something new. Nothing is marked done by itself, and nothing changes on GitHub. An issue's labels also help pick skills: a skill whose `metadata.claudio-tags` include one of them scores as if the session had that tag.
- **Assistant Settings** (the panel's ⋯ menu, per project): the mode (**Automatic**, the default: background work and follow-up offers; **Manual**: only what you ask for; **Off**: notes and the plan by hand, no Claude calls), **Don't send transcripts** (follow-ups then read only the session's final message and the files it changed), and the models for quick checks and for follow-ups (Haiku, Sonnet or Opus). A line under the project name says when the assistant is off (with Turn On), when background work is paused and how many jobs are waiting (Limits… opens Settings › Assistant), or that it's in Manual. Background work that's held back (over the usage threshold, spending credits, or at the daily limit) waits and runs once it can; a note you capture is checked then. The **Activity Log** (⋯) lists every Claude call in the project, newest first, with its model, time, cost and result (Done, Waiting or Failed); a Failed one opens **Job Failed**, with Try Again. Settings › Assistant also sets how many background calls a day an API key, Bedrock or Vertex sign-in can make (20 by default).
- **What sessions get:** every session Claudio starts gets Claudio's plugin (`--plugin-dir`, written to `~/Library/Application Support/Claudio/plugin/claudio/` at launch) and the project's skills folder (`--add-dir`, `assistant/<project id>/skills`, whose `.claude/skills` holds approved skills). So does a direct session each time its terminal opens. A background agent that's resumed doesn't, because resuming one with flags starts a copy, so agents started before this build go without. The plugin puts a `claudio` command on the session's Bash PATH, which the session may run without asking (its settings allow `Bash(claudio:*)`): `claudio plan` prints the plan with each item's id, `claudio item <id>` prints one item with its notes, and `claudio note "<text>"` (or `claudio note -` to read standard input) saves a note of up to 4,000 characters, and `claudio suggest "<text>"` proposes a plan change, which waits in Needs You. Outside a Claudio project they refuse rather than lose the text. Its `/claudio:note` skill tells the session when a note is worth writing. Notes a session writes appear marked with its name, have Undo, and join the plan item the session is working on. They go through `assistant/inbox.log`, which Claudio reads every half second and at launch, so notes written while Claudio was closed still arrive.
- Notes and the plan are kept per project in `~/Library/Application Support/Claudio/assistant/<project id>/`: `assistant.json`; `audit.jsonl`, a log of every change and every call; and `suggestions.json`, the suggestions showing on notes; `settings.json`, the project's Assistant Settings; `skills.json`, lessons, skill drafts, approved skills' records and which sessions used them; `history/`, every approved version of each skill; `retired/`, retired skills; `sessions/`, plan-item sessions' own skill sets; `github.json`, Mark Done suggestions you said Not Yet to; and `plan.md`, the copy `claudio plan` reads. An entry in `assistant.json` that can't be read is left as it was, and the panel counts it.
