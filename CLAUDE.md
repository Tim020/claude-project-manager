# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Claudio is a native macOS app (SwiftUI, macOS 14+) for running and organising many Claude Code sessions. It drives the `claude` CLI: each tab is an embedded terminal attached to a Claude Code background agent. See `README.md` for the feature list, and `design/` for the original Claude Design handoff.

## Commands

```sh
swift test                                    # full suite (macOS, or Linux with a toolchain)
swift test --filter EnvironmentCheckTests     # one test class
swift test --filter EnvironmentCheckTests/testSignedOut   # one test
./scripts/test-linux.sh                       # no local toolchain: runs the suite in the swift:6.1-noble Docker image
./scripts/test-linux.sh --filter TitleSyncTests          # extra args are passed to `swift test`
swift run Claudio                             # run from the package (no notifications; see below)
./scripts/build-app.sh [--no-open]            # build/Claudio.app + zip; opens it unless --no-open or CI
```

- Behind an HTTPS proxy, `test-linux.sh` passes the proxy variables through, and mounts `$SSL_CERT_FILE` when that's set.
- CI (`.github/workflows/ci.yml`) runs on pull requests, pushes to `main` and manual dispatch. It runs the tests on Linux (`swift:6.1-noble`) and on macOS 15 (Xcode 16.4). The macOS job also runs `build-app.sh` and uploads `Claudio.zip`. The macOS job is the only place the SwiftUI layer gets compiled, so when working without a Mac, check its result after pushing UI changes.
- There's no linter. Keep builds warning-free.

## Architecture

**Two targets, one rule: logic lives in `ClaudioCore`.**
- `ClaudioCore` (library) builds and is tested on Linux. It holds the models, workspace operations, CLI command builders, parsers, persistence and `AppModel`, the `@Observable` main-actor model the whole UI reads.
- `Claudio` (executable) is a thin SwiftUI/AppKit layer. Every file is wrapped in `#if os(macOS)`, and `LinuxStub.swift` provides `main` on Linux. It owns the SwiftTerm terminals (`TerminalRegistry`), notifications (`SessionNotifier`) and all views.
- New behaviour goes in core, with tests. The UI calls into `AppModel`.

**Data model.** Project (a working directory) → Folder (the user's grouping, nesting inside other folders without limit) → Session (one Claude Code conversation). A `Folder`'s `parentID` points at the folder it sits inside (nil at a project's top level); storage stays the flat `Project.folders` it always was, and sibling order (at any depth) is still relative order within that array. `Workspace.relocateFolder` is the one move primitive (reparent, optionally into a different project carrying the whole subtree and re-homing its sessions, then position among the new siblings); `moveFolder(toProject:)`, `moveFolder(intoFolder:)` and `moveFolder(before/after:inProject:)` are its public shapes. It guards against a folder moving into itself or its own subfolder (`WorkspaceError.cyclicFolderMove`), and `Project.sanitizedFolders` breaks a cycle already in a decoded file (a corrupted `state.json`) by clearing just the edge that closes the loop. `deleteFolder(mode:)` either promotes its direct contents up one level (`.promoteChildren`, the generalization of "becomes Unfiled" once there's a parent to receive them) or drops its whole subtree to Unfiled (`.flattenToUnfiled`); the sidebar only asks which when the folder actually holds something. Folder-level aggregates — status pills, Archive Completed, Close Completed Tabs, the pull request chip and overview — roll up a folder's whole subtree (`sessionsInSubtree`, `subtreeFolderIDs`), while `sessions(in:)` stays direct-children-only for what a folder's own row lists; the project header sums only top-level subtrees (plus Unfiled) to avoid double-counting nested ones. `Sidebar.build` flattens the tree into a pre-order list with a `depth` per `SidebarFolder`, so the view renders it with one flat `ForEach` rather than recursing; an ancestor shows if anything in its subtree matches the active filter, even when it doesn't match itself. Breadcrumbs, pickers and PR group headers — anywhere a folder is named outside the indented tree itself — use `Workspace.path(of:)` ("Backend › Auth › OAuth") rather than its bare name, since nesting means two folders can share a name. `Workspace` holds these and the ordered open tabs (`openTabIDs`), which span all folders. A tab is a session's id, or an `OverviewTab`'s (a project's or folder's Pull Requests, in `overviewTabs`, which lasts only while its tab is open). So a tab id isn't always a session: use `Workspace.isTab`, and `AppModel.paneTabs(inPane:)` for what a pane shows. `selectedSessionID` is the focused tab, which may be an overview (`selectedOverview`). `PersistedState` (workspace + `AppSettings`) is saved as JSON to `~/Library/Application Support/Claudio/state.json`. Decoding is tolerant: new fields use `decodeIfPresent` with defaults, and `PersistedState.currentVersion` handles migrations. The Project Assistant's data (notes and plan items; design in `design/Project Assistant Backend.md`) is kept apart, per project, by `AssistantStoring`: `assistant/<project id>/assistant.json`, an append-only `audit.jsonl`, `suggestions.json` (the suggestions showing on notes: throwaway, so no audit or version), `plan.md` (what `claudio plan` prints) and `skills/` (the `--add-dir` root). Sessions write notes to `assistant/inbox.log` through the plugin's `bin/claudio` (`ClaudioPlugin`, embedded in core and written to `plugin/claudio/` at launch), read from a saved offset by `InboxReader`. `AppModel` defaults to `MemoryAssistantStore`, so tests never touch real files, and a project whose file can't be read is never written to.

**How sessions run.**
- New sessions are dispatched as background agents: `claude --bg --settings <hooks> -- "<prompt>"`, which prints `backgrounded · <8-hex id>`. The worktree option goes in the same settings JSON as `worktree.bgIsolation` (`worktree` or `none`), not as `--worktree` (see below).
- A tab is a SwiftTerm terminal running `claude attach <id>`. Closing a tab only detaches; stop is `claude stop`, delete is `claude rm`.
- Command builders are `AgentCommands` and `TerminalLaunch` in `Agents.swift` and `ClaudeLaunch.swift`. They run through the login shell so `PATH` matches the user's terminal. Frequent polling skips the login shell for speed.
- If background agents are off or unsupported, a tab runs `claude --session-id/--resume` directly.

**Where session status comes from.** Three sources are merged in `AppModel`:
1. **Hooks.** `HookSettings` passes `--settings` JSON whose hooks append `<app session UUID>\t<hook JSON>` lines to `hook-events.log`. `pollHookEvents` (every 0.5 s) feeds them to `HookReducer`. Events are routed by their own `session_id` first, not only by the app UUID, because a CLI-made copy inherits the original session's settings. See `hookTarget(for:)`.
2. **`claude agents --json --all`** (every 3 s), applied by `apply(_:)`. A session stays linked to the agent it's attached to; only unclaimed sessions are matched by conversation id. Its `status` (busy/idle/waiting) is the process; its `state` is Claude Code's view of the task, which stays `working` while it thinks the task goes on (waiting on CI, say), even idle after a Stop. So `BackgroundAgent.sessionStatus` takes Working from `status` (seen with 2.1.285). An agent with no pid is Completed whatever its `state`: `claude stop` sets `state: "stopped"`, but agents whose process went some other way keep the state they had, `blocked` included, and nothing waits on those (2.1.285; `Fixtures/agents-after-stop.json`, recorded in a container, and `agents-stopped-blocked.json`, from a real listing). An idle agent leaves a session on Awaiting Input when the hooks set that (a question at the end of a turn), but not when the list itself had said waiting since the hooks last reported, or once the process has gone. "Stopped unexpectedly" reads the task state directly (the process went while the task was still `working`), and a stop you asked for (`AppModel.stop`) isn't notified at all until its agent is seen gone.
3. **History files** in `~/.claude/projects/<cwd with non-alphanumerics → '-'>/<sessionId>.jsonl`, read by `SessionDiscovery` in the background (cached by mtime and size) every 30 s. They give titles, summaries, PR links, context estimates and imported sessions. They must never override the status of a session that's live (a terminal here, or a running agent). See `liveSessionIDs`.

The status line (`StatusLineCapture`) records only `context_window`, per session. **Plan usage has one source: `claude -p /usage --output-format stream-json --verbose`, polled at launch and every 60 s** (`AppModel.usageRefreshInterval`). It makes no model call. Each `-p` run fires the user's SessionStart hooks, so it passes `--settings '{"disableAllHooks":true}'`, which leaves the report unchanged (2.1.283; 2.1.169 accepts it). Each reading replaces the last, and a failed read keeps it; output that parses to nothing is logged once. Don't take `rate_limits` from the status line: each session reports the figures from its own last request, so idle sessions repeat stale ones (that made the sidebar bar jump between sessions' readings). `/usage` fetches `GET /api/oauth/usage` behind a 60 s cache (`cachedUsageUtilization` in Claude Code's config), shared by every process (read from the 2.1.283 binary; `--debug-file` logs "Usage read answered from a snapshot Ns old"). The binary also skips the cache when rate-limit headers newer than it have been seen, but that state appears to live in memory in one process, so a fresh `claude -p /usage` never has it (not tested). So a reading is up to 60 s old, and the sidebar up to about 2 minutes behind. Its assistant event carries a `usage_report` with `limits[]` (exact `resets_at`) and `extra_usage` (usage credits, in minor units); the plain text has neither. "Using credits" is worked out from a window at 100% plus credits enabled (`UsageSnapshot.isUsingCredits`), because in `-p` mode the text's "using your overages" header isn't reliable. The plan name comes from `claude auth status`.

**Observation churn.** Polling runs constantly, so mutate a copy and assign only when it differs; don't write to observed state on every tick. The menu bar reads only `menuFlags`, to stop menus redrawing. Periodic work runs in `.task { await Polling.every(…) }` loops, never `onReceive(Timer.publish(…).autoconnect())`. `ContentView`'s body reads `model.settings` (so all of `state`) and is re-evaluated whenever any session changes, and each re-evaluation restarted those timers, so the longer ones rarely fired while sessions were busy.

## Claude Code CLI behaviour Claudio depends on

These were verified against real CLI output, which is recorded in `Tests/ClaudioCoreTests/Fixtures` and in the tests. Minimum version: 2.1.169, the first with `agents --json --all`.

- **Resuming a background agent with any flags starts a copy.** Claude Code prints `…the flags you passed started a copy as <id>`. So `resume(session:prompt:continuingAgent:)` passes no flags when continuing an existing agent. Copies are detected by `AgentListParser.copiedID` and kept as separate "(copy)" sessions.
- **A prompt starting with `-` is read as an option**, quoted or not. `claude '- [ ] Bug…' --bg` still prints `backgrounded · <id> (idle — send a prompt to start)` and exits 0, but the agent then fails (`state: "failed"`, "exit 1 before init: error: unknown option"). A direct `claude '- …' --session-id …` exits at once with the same error. So every command puts the prompt last, after `--` (`TerminalLaunch.promptArguments`). Checked in a container with 2.1.169 and 2.1.283: `--` survives the agent's respawn, the prompt arrives unchanged in both `--bg` and direct mode, and `claude --bg --resume <id> -- '<prompt>'` resumes as the old argument order did. 2.1.283 wakes the same agent. 2.1.169 gives a stopped agent a new id either way.
- **Resuming a session that's open in an interactive terminal elsewhere also makes a copy.** Claudio asks the user first.
- **`/clear` starts a new conversation in the same process.** The hooks give `SessionEnd` (`reason: "clear"`) for the old id, then `SessionStart` (`source: "clear"`) for the new one, both under the tab's app UUID (`Fixtures/hook-clear.log`, from a live 2.1.284 session). `claude agents --json` then lists the agent's `sessionId` as the new id (seen with 2.1.289). The old `<id>.jsonl` stays behind, so `Session.adoptConversation` keeps it in `replacedConversations`, and discovery doesn't import it (that was a stray Unfiled session). A transcript is read from the newest of `historyItems`, since a conversation that entered a worktree carries on in the worktree's history folder while the session may still name the repository.
- **Stopping closes the tab's terminal before the agent has gone.** The agent stays listed alive until the next poll, so a tab shown then must not auto-attach (`AppModel.attachIfLive`, `isStopping`).
- **← on an empty prompt in an attached terminal switches to the agents view.** Its title is "claude agents". `AgentsViewDetector` and `TerminalRegistry.returnToSession` reattach the tab.
- **Titles.** `/rename` writes `{"type":"custom-title","customTitle":…,"sessionId":…}` to the history file. Claudio writes the same record when renaming (`SessionTitleWriter`) and follows new ones from the terminal. `Session.claudeTitle` stops a rename bouncing back and forth.
- **Two failure hooks** (recorded in `Fixtures/hook-failures.log`, accepted by 2.1.169): `PostToolUseFailure` fires when a tool runs and fails (a Bash command exiting non-zero too), with `error` as a string and `is_interrupt`. `StopFailure` fires *instead of* `Stop` when a turn ends with an API error (`error: "authentication_failed"`…), so it has to end the turn. `PermissionDenied` didn't fire for a default-mode denial, so it isn't used.
- **Background tasks.** `Stop` carries `background_tasks`: `{id, type, status, …}` for each backgrounded Bash command, Monitor (both `type: "shell"`) and async subagent (`"subagent"`) still running as the turn ends (2.1.289; `Fixtures/hook-background-tasks.log`). Each one finishing wakes the session with a new turn, a `UserPromptSubmit` whose prompt is a `<task-notification>`. A task that finishes mid-turn is absorbed into that turn with no hook of its own, so the next `Stop`'s list is what counts: `Session.backgroundTasks` holds it (`BackgroundTask`: id, kind, description, and when first seen, kept across Stops), and the session stays Working while it isn't empty, even with the agent idle (`apply(_:)`). The agent's process ending (or its leaving the list), `SessionEnd` or a `Stop` without the field clears it. `StopFailure` has no `background_tasks` (2.1.289, an invalid API key in a container; `Fixtures/hook-stop-failure-2.1.289.log`). Its turn may have been woken by a task ending, or seen tasks end with no hook, so it drops the list (one still running wakes the session later, and that Stop lists it again) but keeps the marks. A `<task-notification>` prompt with a `<status>` also drops its task straight away (`TaskNotification`); a Monitor's events have no `<status>`, and a resumed subagent may notify again. A task that never ends (a dev server) would hold it forever, so after `BackgroundTasks.longRunningAfter` (30 min) the session is in Needs You (`longRunningSessions`, assistant on or off), and `markBackgroundTasksFinished` records its ids in `finishedBackgroundTasks`, which later Stops leave out while they still report them. It's all saved, and checked at launch, because hooks written while Claudio was closed are skipped: a background agent's job state, `~/.claude/jobs/<short id>/state.json`, has a `fan` of its tasks (`{id, kind, label, startedAt}`, plus `doneAt` when finished; same ids as the hook; `Fixtures/job-state.json`), and the entries without `doneAt` replace the saved list (`BackgroundJobState`). `fan` isn't a full history (finished entries dropped out once a new task started), but running tasks were always in it. Without a job state the saved list stands. Launch still shows every session as not Working; the first agent list puts one back to Working once its agent is seen alive, so an agent that died while Claudio was closed never looks as if it had just finished. Sessions without an agent ended with the app. In the live hook log, the "Notification Grouping" session from #31 had no tasks running at its last Stops, so this doesn't bring that back.
- **Transcripts, for Usage** (`TranscriptUsage.swift`, `UsageLedger.swift`; a probe over this Mac's real transcripts, 2.1.289: 9,602 replies, 423 of them with lines that grew, all in subagent transcripts, and 81 ids in two transcripts. `Fixtures/transcript-usage.jsonl` is built in the shape of real lines, not recorded; its growing reply is in a main transcript, where none was seen, but the rule is the same). One reply is written as several lines, a line per content block, each with the same `message.id` and `usage`, and in subagent transcripts (`<id>/subagents/agent-*.jsonl`, beside `*.meta.json`) the later lines have more `output_tokens`, so the last line of an id counts. The scanner matched the probe's totals exactly on a 4.7 MB transcript. A reply's lines were always consecutive. A copy of a conversation repeats the original's replies under the same ids (81 of 9,500 ids sat in two main transcripts), so a project counts each id once, for the oldest session. `usage.cache_creation` splits cache writes into `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens`, `usage.speed` is `"standard"` or `"fast"`, and API errors are `model: "<synthetic>"` replies. Prices are in `UsagePricing.table` (from the claude-api skill, cached 2026-09-25), matched by longest prefix.
- **`claude auth status --json`** exits 1 when signed out but still prints JSON with `loggedIn: false`. `claude auth login` signs in (Console / API-key sign-in is tracked in issue #1).
- **`claude rm` leaves the history behind.** It removes the agent and its worktree, but `<sessionId>.jsonl` (and the `<sessionId>/` folder of subagent transcripts and tool results) stays in `~/.claude/projects`. The agent even writes to it while stopping. Verified with 2.1.283. So deleting from Claude Code removes those files itself, after the `rm` (`AppModel.removeHistory`).
- **The assistant's session flags (`--plugin-dir`, `--add-dir`) go on every launch except continuing a background agent**, which would start a copy: `AgentCommands.dispatch`, `resume(continuingAgent: false)`, and every direct `TerminalLaunch.make` (`--session-id` and `--resume`: each is a new process). `Session.hasAssistant` records sessions that got the plugin, so they can write notes. Their `--settings` JSON also allows `Bash(claudio:*)`: in Ask mode, `claudio` was denied without it. Both work with a path containing a space (`Application Support`), checked with 2.1.284. Skills under an `--add-dir` root load only when project settings are loaded: `--setting-sources ''` (the assistant's own `-p` calls) turns them off, while the plugin's skills and `bin/` still load.
- **Don't start background agents with `--worktree`.** The background-session system prompt says "If you didn't enter the worktree yourself this job… ask before committing", so an agent started in a worktree won't commit its work. With `worktree.bgIsolation: "worktree"` (the default), edits in the main checkout are blocked until the agent calls EnterWorktree itself, and then it commits and pushes. `"none"` lets it edit in place. The prompt text and the setting were read from the 2.1.283 binary. A container run with 2.1.283 showed that the agent process gets the `--settings` JSON, and that the job's `respawnFlags` (in `~/.claude/jobs/<id>/state.json`) keep it for respawns. Once an agent that entered a worktree itself has stopped, `claude agents --json` lists the repository as its `cwd`, and the worktree is only in the job state (`worktreePath`). So Claudio also finds it from the session's edits (`ChangesDirectory`).
- **Background agents live in `<repo>/.claude/worktrees/<name>`.** Their history directories are prefixed `<encoded repo>--claude-worktrees-`, and they're grouped under the repository's project.
- **The assistant's `claude -p` calls** (`AgentCommands.assistant`, `AssistantReplyParser`):
  - They use `--setting-sources ''`. With 2.1.284, loading the user's settings sometimes let Haiku consult an Opus advisor tool the user had configured, at about 20 times the cost. `user` is loaded only when signing in may need it (`AssistantSettingSources`).
  - A failed call still prints `"subtype": "success"`. `is_error: true`, `terminal_reason: "api_error"` and exit 1 are what tell, with the message in `result` ("Not logged in · Please run /login"). An exceeded `--max-budget-usd` says `"subtype": "error_max_budget_usd"`, `terminal_reason: "budget_exhausted"`, with no `result`. Recorded in `Fixtures/assistant-*.json`.
  - By default a rejected API key retried for 190 s. With `CLAUDE_CODE_MAX_RETRIES=2`, which the calls set, it fails in about 3 s with the real error. Each call also has its own timeout (`TerminalLaunch.timeout`, reported through `CommandResult.timedOut`).

**Other tools.**
- `git` is read-only here: it runs with `GIT_OPTIONAL_LOCKS=0`.
- `gh` is optional. Recorded output: signed out from gh 2.63.2, signed in from 2.101.0. `gh pr view` also returns merged or closed PRs, so only `state: OPEN` counts.
- Pull Requests overviews (`AppModel+PullRequests.swift`) use `gh repo view`, `gh pr list/view --json` (`GitHubCLI.overviewFields`) and `gh api graphql` for unresolved review threads. Recorded output (DigiScript #1427, gh 2.101.0) is in `Fixtures/gh-pr-view.json` and `gh-review-threads.json`. Checks without a workflow (SonarCloud, CodeQL's summary) have `workflowName: ""`. The lists stop at their limits (100 open, 40 recent), so counts come from `gh api graphql` totals (`GitHubCLI.pullRequestTotalsQuery`: all/open/merged `totalCount`; recorded in `Fixtures/gh-pull-request-totals.json`). With PRs without a session included, Merged and All also load the whole history (keeping its merged and closed rows; open ones come only from the open list), `gh pr list --state all --limit ≤5000 --json GitHubCLI.historyFields` (recorded in `Fixtures/gh-pr-list-history.json`, gh 2.101.0). Its rows have `hasDetails == false`, and a row loads its details with `gh pr view` when hovered or clicked. The fields matter: on DigiScript's 1,201 PRs, `overviewFields` failed with HTTP 504, `additions,deletions` took 93 s, and `historyFields` took 9 s. When the history reloads is `ProjectPullRequests.needsHistory`. A session is tied to a pull request only when a tool call acted on it (`PullRequestActivity`: `gh pr create` output, `gh pr review/comment/…` targets, `gh api` writes, GitHub MCP tools), recorded in `Session.pullRequests` as opened or reviewed. A number with no repository (`gh pr review 12`) is stored as `#12` and resolved against the project's repository. Always read a session's pull requests through `AppModel.pullRequestLinks(ofSession:)`, which drops other repositories'.
- Files Changed's "vs" branch comes from, in order: the PR's base (`gh pr view --json baseRefName,number,state`, cached for 5 minutes), then `Project.comparisonBranch`, then `origin/HEAD` or `main`/`master` (`GitChanges.load(preferred:)`).

To check CLI behaviour without touching the user's setup, install it in a container:

```sh
docker run --rm node:22-slim bash -c 'npm i -g @anthropic-ai/claude-code@<version> && claude …'
```

A fresh container is signed out, with an empty config. Any claim about CLI output should be backed by such a run or by output the user pasted.

## Testing conventions

- **Don't mark an `XCTestCase` subclass `@MainActor`: it breaks test discovery on Linux.** Hop inside the test instead: `try MainActor.assumeIsolated { … }`, `await MainActor.run { … }`, or `@MainActor` helper methods.
- `AppModel` is fully injectable: store, discovery home, hook log URL, command runner, `locateClaude`, `now`, `home`. Use `MemoryStore`, `FakeRunner` (canned CLI output, and it records the arguments it was called with) and `FakeTerminals`. `FakeRunner` and `FakeTerminals` are defined in `AgentModelTests.swift` and `AppModelTests.swift`.
- `model.terminals` is a weak reference, so keep `FakeTerminals` in a stored property.
- Some `internal` helpers exist only for tests: `applyStatus`, `applyNeedsAction`, `applyAgentLink`, `applyTestSession`.
- `AppModel` resets Working sessions to Completed at launch. Tests that need a non-completed session after init should use Awaiting Input.

## Build and dependency constraints

- The package is `swift-tools-version:5.10`, in Swift 5 language mode.
- SwiftTerm is pinned to `exact: "1.20.0"`, because newer versions need tools 6.2. It's a macOS-only dependency of the `Claudio` target.
- Notifications need the bundled `.app`, not `swift run`.
- `build-app.sh` signs with an Apple Development or Developer ID certificate if the keychain has one (override with `CODESIGN_IDENTITY`). Otherwise it signs ad hoc, and macOS then forgets folder-access and notification permissions on every rebuild.
- The app icon in `Resources/Assets.xcassets` is light only. The dark variant (`design/app-icon/`) needs an Icon Composer `.icon` file.

## Working in this repo

- Work on a feature branch and open a pull request into `main`; don't push to `main` directly. Name branches by kind: `feature/…`, `fix/…`, `ci/…`, `docs/…`.
- CI runs on every pull request (and again on `main` after merging). Check the PR's checks before merging, the macOS job in particular: it's the only place the SwiftUI layer compiles. Each run uploads the built `Claudio.zip`, so a PR can be tried before it merges.
- Keep `README.md`'s feature list current when behaviour changes. Log user-visible actions and CLI commands in the Activity Log (`log.append`), but never account details (see `run(_:hideOutput:)`).
